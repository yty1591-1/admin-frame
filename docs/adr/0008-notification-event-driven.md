# ADR-0008：通知中心事件驱动编排（业务域只写 Outbox）

日期：2026-11-04　状态：已接受
关联：ADR-0006（租户即隔离边界）、ENT-10、`docs/archive/plans/notification-center-plan.md`、`docs/notification-channels.md`（渠道驱动 M4）

## 背景

渠道驱动包（`pkg/sms|email|push|webhook`）与异步底座（`pkg/outbox`：事务性
Outbox / Relay / DLQ）均已就绪，但 `internal/` 层没有任何编排：模板、偏好、
频控、重试、状态查询全部缺失。首个真实调用方已经出现——T-14 邀请邮件
（此前「只落库不发送、运营线下转交」）与租户停用前客户通知。

生产就绪规划 5.1.3 已给出铁律：**业务域只写 Outbox 事件，通知中心订阅；
禁止在业务事务里同步调用外部渠道**。本 ADR 固化该决策的实现形态与例外。

## 备选方案

1. **事件驱动**：业务域在事务内写 `notification.requested` Outbox 事件，
   通知中心（worker 进程）异步消费、编排投递；
2. **同步 RPC**：业务域事务提交后同步调用通知域 HTTP/gRPC 接口；
3. **共享库直调**：业务域直接 import 通知域 app 层同步发送。

## 决策

采用**方案 1（事件驱动）**，并对唯一一类场景开受控例外。

### 1. 事件驱动而非同步调用

- 「库已写、通知必达」只有事务性 Outbox 能保证：同步调用在进程崩溃 /
  下游超时时必然出现「业务成功、通知丢失」，而通知失败又不能回滚业务
  （邀请已经创建，邮件失败再回滚就是事故）；
- 事务内只做一次本地 INSERT（Outbox 事件），无跨进程写，延迟可控；
- 重试、频控、熔断、DLQ 全部复用 ENT-03 的 Relay 机制，通知域不重复造
  可靠性轮子（对齐「不在低流量阶段引入 Kafka」的既有决策）。

### 2. 编排管道固定顺序（唯一真相在 `internal/notification/app`）

幂等去重 → 过期判定 → 黑名单 / 偏好过滤（fail closed）→ 渲染 → 频控 →
熔断包住发送 → 主备降级（仅可重试错误 + 熔断 Open）→ 状态回写。
驱动内绝不重试；通知单状态机单调不回退，渠道明细承载全部中间态。

### 3. 唯一例外：验证码同步旁路

登录 / MFA 验证码是强交互场景（用户正盯着输入框），异步排队不可接受。
保留 identity 直连 `pkg/sms` 的同步路径，但收敛到受控门面并明确禁令：
**仅验证码类场景允许；业务通知禁止走旁路**（频控收敛在 NT-10 完成）。

### 4. 补偿语义：失败落 DLQ、重放走新请求

失败通知（预算耗尽 / 永久错误）以 `retry.Permanent` 进 `async_dlq`——
DLQ 载荷是渲染参数与地址的**唯一持久副本**（通知表按 PII 最小化不存明文）。
人工补偿经 `ReplayService` 从 DLQ 读载荷，生成**新事件 + 新通知单 +
新幂等键**（`notify:replay:<newID>`），原请求保留为审计痕迹。防重复由
幂等键唯一约束兜底，天然对抗重放风暴。

### 5. PII 边界

| 数据 | 位置 | 理由 |
|------|------|------|
| 渲染参数 / 地址 / token 明文 | 事件载荷 + DLQ + 渲染瞬时内存 | 随 Outbox retention 清理，不进 90 天保留的通知表 |
| 收件人引用 | 通知表（subject_id 或 SHA-256 摘要） | 可对账、不可还原 |
| 黑名单目标 | 加盐 HMAC（64 hex） | 拖库不可枚举；盐强制环境注入，缺盐拒绝启动 |
| 验证码 / 邮件正文 | 永不落库、不入日志 / 指标标签 | 指标标签只允许低基数枚举 |

## 后果

- 业务域接入通知 = 事务内一次 `Dispatch`（租户邀请已接入，端口
  `tenant/app.InvitationNotifier`）；A 端代发 / DLQ 重放复用同一出口；
- 渠道生产驱动（SMTP / 阿里云 / APNs）配置就绪后经 `NewWithRoute`
  注入，编排逻辑零改动（当前默认 memory 驱动，M4 阶段语义）；
- 通知查询 / DLQ 重放 / 代发的管理端 API（NT-06）与回执回调（NT-07）
  在此决策框架内补齐，不改变编排语义。
