# ADR-0006：租户即隔离边界，`tenant.id` 直接作为 `merchant_id`

- 状态：已接受（ENT-09 落地）
- 日期：2026-11-03
- 关联：ENT-09、ENT-12（数据范围契约）、ENT-14（租户配额）、ADR-0005

## 背景

平台此前没有租户主数据：B 端隔离依赖 `merchant_id` 字符串，值从令牌与请求传入，
数据库里没有任何地方能回答「这个商户是谁、是否还在服务期、什么时候停用过」。
`identity_account`、`iam_role`、`iam_binding` 等表都以 `VARCHAR(64)` 存该值，
空串表示平台级（A 端），非空表示商户级（B 端）。

ENT-09 要引入租户生命周期（`pending → active → suspended → terminated`），
必须先决定租户与既有 `merchant_id` 的关系。三种可选形态：

1. **独立主键 + 映射表**：`tenant(id, code)`，业务表继续用 `merchant_id = tenant.code`，
   中间加 `merchant_tenant_map`；
2. **双主键并存**：`tenant.id` 与 `tenant.code` 都对外暴露，由调用方自行选择；
3. **同值**：`tenant.id` 就是 `merchant_id`，业务表存的值即租户主键。

## 决策

采用**方案 3**：

1. `tenant.id` 是隔离边界，`VARCHAR(64)`，与既有 `merchant_id` 宽度一致；
   业务表不需要改列、不需要映射表、不需要回填。
2. **不引入 `tenant.code`**：多一个对外标识就多一处「用哪个查」的分歧，
   而租户改名 / 改编码的需求并不存在；展示名称用 `tenant.name`。
3. **状态机不可跳过、不可回退**：`pending → active → suspended → terminated`，
   其中 `terminated` 为终态。暂停可直接终止，但恢复必须经过 `active`；
   禁止 `suspended → pending`（会让已开通租户丢失开通事实），
   禁止 `terminated → *`（复活等于绕过合同与结算，需新建租户）。
4. **停用与终止必须给原因**（`reason`），与状态一起落库并进审计；
   仅凭操作人无法回溯「为什么停的」。
5. **并发用乐观锁**：`tenant.version` 每次成功迁移 +1，`UPDATE ... WHERE version = ?`；
   冲突返回 409 而不是后者覆盖前者。
6. **权限只授予平台侧**：`tenant:read` / `tenant:write` 仅 A 端可授。
   让 B 端管理自己的租户记录，等于允许租户自行「恢复」被停用的账号。
7. **成员与配额随用例落地**（同批次补齐，不预留死表）：
   - `tenant_member` 主键 `(tenant_id, subject_id)`，重复添加幂等；**停用代替物理删除**，
     否则「曾在过这个租户」的事实会丢，离职回溯与权限审计都依赖它；
   - 「至少一名在册 owner」是跨行不变量，SQL 无法表达，由应用层在降级 / 停用时校验；
   - 成员只区分 `owner` / `admin` / `member` 三级，**不复制 IAM 权限模型**：
     细粒度权限仍由角色绑定解析，租户成员表只回答「谁属于这个租户」；
   - `tenant_quota` 只存上限（`-1` 表示不限），**不做用量计数**：执行属 ENT-14，
     两个域通过表解耦，避免租户主数据被限流状态污染。

## 后果

- `merchant_id` 的语义从「自由字符串」收紧为「必须存在的租户 ID」。
  存量数据不回填：库里已有的 `merchant_id` 在租户表建行之前仍然可用，
  但一旦启用租户守卫（下一步），未登记的 `merchant_id` 将无法通过校验——
  上线顺序必须是「先导入存量租户 → 再开启守卫」，此约束写入上线清单。
- 停用生效由 `app.Guard` + `platform.WithTenantGuard` 实现（T5）：状态缓存 TTL 30s、
  负缓存 5s，同进程迁移后立即失效，跨副本最坏 30s 收敛，满足「停用 ≤ 60s 拒绝访问」。
  守卫**不校验令牌**，只按 `merchant_id` 判租户状态；令牌撤销仍由身份域负责，
  两者正交——停用租户后再恢复，用户无需重新登录。
- 守卫是 fail closed 的：仓储不可达返回 503 而不是放行。代价是数据库故障会同时
  影响 B 端可用性，这与「停用必须真实生效」是同一枚硬币，取舍记录在此。
- 数据处置（终止后保留多久、是否匿名化）留给 ENT-15；本 ADR 只保证终止不可逆。
- 若未来真的需要「一个租户多个商户主体」，再引入 `tenant_member` 并在
  ADR 中记录，不在本表预留字段。

## 备选方案与放弃理由

- **映射表（方案 1）**：多一次 join、多一处不一致可能；迁移期要双写，回滚要清表，
  而收益（租户可改编码）无需求支撑。
- **双主键（方案 2）**：接口与审计里会出现「有的地方用 id、有的用 code」，
  排查时最容易出错；契约审查成本高于收益。
- **软删除 + 状态列并存**：`deleted_at` 与 `status=terminated` 会形成两套「已删除」判断，
  迟早出现「软删了但状态还是 active」的脏数据。
