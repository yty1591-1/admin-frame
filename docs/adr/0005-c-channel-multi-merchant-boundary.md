# ADR-0005：C 端多商户边界与演进触发条件

- 状态：已接受（V1 边界）
- 日期：2026-11-01
- 关联：BIZ-09、`docs/identity-authn.md` §19、ADR-0003

## 背景

A / B / C 三端身份域已落地（ADR-0003）。B 端以 `merchant_id` 做行级隔离；
C 端账号（手机号 / OAuth 主体）当前不属于任何商户，`identity_account` 唯一键为
`(channel, merchant_id, subject_index)`，C 端 `merchant_id` 恒为空串，因此主体在平台内全局唯一。
产品侧提出的「同一手机号在不同商户下独立注册」尚无明确需求与结算模型，
若提前引入会同时改动契约、令牌 claims、缓存键与迁移，成本与回滚风险不可逆。

## 决策

1. **V1 维持 C 端全局单租户**：C 端账号、会话、撤销与审计均为平台级，`merchant_id` 恒为空串。
2. **不预留半成品字段**：C 端不写入 `merchant_id`，避免「字段存在但语义未定义」的假多租户。
3. **演进触发条件**（满足任一即启动产品决策，不满足则继续保持单租户）：
   - 同一部署环境需要承接两个及以上商户，且各商户对 C 端账号有独立注册 / 数据隔离的合规要求；
   - 商户要求 C 端账号、审计或数据导出按其租户独立保留与销毁；
   - 需要按商户维度做结算、限流或风控，且无法在网关层以入口维度完成。
4. **演进路径**严格按 `docs/identity-authn.md` §19.2 执行：契约 → 数据 → 仓储 → 治理 → 回滚，
   必须按新 major 契约发布，单租户与多租户不兼容。
5. **回滚策略**：切换窗口内旧令牌只读，新令牌强制重新登录；数据层保留原唯一键直至回填校验通过，
   回滚时以旧唯一键重新签发令牌，不改写已迁移账号。

## 后果

- C 端实现保持简单，缓存键与令牌 claims 不引入未使用维度。
- 多商户 C 端成为显式的产品决策，而非「未完成的技术遗留」；触发条件与迁移步骤已文档化。
- 一旦触发，需要一次 major 契约升级与数据回填，成本已在 §19.2 列明，不接受增量式兼容。
