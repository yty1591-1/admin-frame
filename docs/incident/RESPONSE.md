# 事故响应流程（声明 → 缓解 → 关闭）

> **状态**：生效中（Normative）  
> **效力**：P1/P2 事故处置的唯一流程依据；与 `RUNBOOK_STANDARDS.md` §5 互补  
> **执行方式**：`check-oncall.sh`（OC-01/OC-06）+ 复盘对照时间线  
> **最后更新**：2026-11-05

目标是让「谁在什么时候做什么」不依赖个人经验：**先定级、再声明、边缓解边通报、关闭后必须复盘**。  
级别判定见 [SEVERITY_MATRIX.md](./SEVERITY_MATRIX.md)；具体处置步骤见 `docs/runbooks/` 对应 runbook。

---

## 1. 生命周期

| 阶段 | 入口条件 | 出口条件 | 责任 | 时限 |
|---|---|---|---|---|
| 检测 DETECT | 告警触发 / 用户反馈 / 巡检发现 | 已记录首个可观测证据（指标、日志、样本） | 发现者 | 立即 |
| 定级 TRIAGE | 有证据 | 按矩阵给出级别与影响面，允许暂定 | 值班（L1） | P1 ≤ 5 分钟 |
| 声明 DECLARE | 级别 ≥ P2 | 事故频道建立、IC 到位、首条结构化通报发出 | 值班 → IC | P1 ≤ 15 分钟 |
| 缓解 MITIGATE | 已声明 | 用户影响消失（指标回到 SLO 内） | IC + OL | 见矩阵缓解目标 |
| 恢复 RECOVER | 影响消失 | 连续观测 30 分钟无复发；数据影响已校验 | OL | ≤ 30 分钟观测窗 |
| 关闭 CLOSE | 恢复 | 行动项已登记、时间线完整、级别与影响定稿 | IC | ≤ 24 小时 |
| 复盘 REVIEW | 关闭 | 复盘会完成、行动项有 owner 与截止 | IC + 域 Owner | P1 ≤ 5 个工作日；P2 ≤ 10 个工作日 |

> 「声明」不是仪式：它的作用是把**信息汇聚点**和**决策权**固定下来，避免多头指挥与重复排查。

## 2. 声明与通报

### 2.1 事故标识

`INC-YYYYMMDD-NN`（当日序号，从 01 起）。标题格式：`[P1] 现象一句话 — 影响端`。  
事故标识在关闭后不再复用；跨日未关闭的事故沿用原标识。

### 2.2 首条通报（复制后填）

```text
[INCIDENT] INC-20261105-01  [P1]
开头：<一句话现象，含端与用户可见表现>
影响：<受影响请求比例 / 租户数 / 是否数据错误>
开始：<UTC 时间，精确到分钟>
IC：<姓名或值班角色>
频道：<事故群链接>
下一次更新：<UTC 时间，P1 默认 +30 分钟>
当前动作：<正在做什么，不要写「排查中」>
```

### 2.3 更新节奏

- P1：每 **30 分钟** 一条，即使没有进展也要写「无进展 + 下一步」；
- P2：每 **2 小时** 一条；
- 阶段变化（DECLARE / MITIGATE / RECOVER / CLOSE）必须单独发一条，不合并进例行更新；
- 对外状态页：仅 P1 且确认客户可见时启用，措辞由 Comms 统一，禁止各端自行发布。

### 2.4 沟通纪律

- 只发**已确认的事实**；推测必须标注「待验证」；
- 不粘贴密钥、令牌、完整连接串、用户个人信息；日志摘录需脱敏；
- 客户名称在对外沟通中使用合同名称，不暴露内部租户 ID。

## 3. 时间线记录

统一写在事故频道置顶文档或复盘文档，**UTC 时间戳 + 标记 + 事实**，一条一行：

```text
2026-11-05T00:12:31Z [ONSET]     首个 5xx 出现在 c-api，错误码 50300
2026-11-05T00:14:02Z [DETECT]    API5xxRateHigh 触发（service=c-api）
2026-11-05T00:16:40Z [ACK]       值班 ack，判定 P1
2026-11-05T00:18:10Z [DECLARE]   建频道，IC=…
2026-11-05T00:31:00Z [MITIGATE]  回滚 c-api 到上一 digest，5xx 回落至 0.2%
2026-11-05T01:05:00Z [RECOVER]   连续 30 分钟无复发，数据校验通过
2026-11-05T01:10:00Z [CLOSE]     行动项 AI-2026-11-05-01/02 已登记
```

必备标记：`ONSET`、`DETECT`、`ACK`、`DECLARE`、`MITIGATE`、`RECOVER`、`CLOSE`。  
复盘必须能从中算出「检测用时」「确认用时」「缓解用时」——算不出来说明时间线不完整，复盘不通过。

## 4. 角色与职责

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **IC（事故指挥）** | 定级与升降级、分配任务、决定是否回滚/降级、对外口径确认、关闭与复盘召集 | 不亲自排查细节（P1 且人手充足时） |
| **OL（操作 Lead）** | 按 runbook 执行处置、维护操作日志、回报每步结果 | 不擅自扩大变更范围；不在未告知 IC 时改配置 |
| **Comms（沟通）** | 按节奏发通报、维护状态页、对接客户成功 | 不承诺未确认的恢复时间 |
| **Scribe（记录）** | 维护时间线与证据链接、记录决策与理由 | 不做技术判断 |

P1 **尽量** IC 与 Scribe 分离（可由非值班同学担任）；单人值班时 IC 可兼任，但必须在时间线标注 `[SOLO]` 并在恢复后补齐记录。P2 允许 IC 兼任全部角色。  
**交接**：跨班必须交接 IC 并在时间线写 `[HANDOFF] 新 IC=…，未完成动作=…`；交接前不得静默下班。

## 5. 与发布、回滚、数据处置的联动

1. **发布冻结**：P1 期间冻结所有非修复性发布（含金丝雀放量）；恢复发布需 IC 同意并在时间线记录。
2. **回滚优先**：疑似由发布引起 → 直接按 [`runbooks/release-rollback.md`](../runbooks/release-rollback.md) 回滚到上一 digest，不在生产上「边查边改」；自动回滚由 `.github/workflows/release.yml` 的 `rollback` job 承担。
3. **迁移不回头**：应用可回滚，schema 不可回滚；已 contract 的迁移按 `DATA_STANDARDS` 处置，禁止 `migrate down`。
4. **数据影响**：出现数据错误/删除时，先止血（停写或回滚），再做影响面统计与修复方案；修复脚本须双人复核并在 staging 验证，执行后留审计。
5. **密钥泄露**：按 [`runbooks/key-compromise.md`](../runbooks/key-compromise.md) 走「先止血后轮换」，与本文并行。

## 6. 关闭标准

同时满足才可关闭：

- [ ] 用户影响消失，核心指标连续 30 分钟在 SLO 内；
- [ ] 若有数据影响：影响范围已量化，修复已验证，审计事件可查；
- [ ] 时间线包含全部必备标记，三个耗时（检测/确认/缓解）可计算；
- [ ] 行动项已写入 [ACTION_ITEMS.md](./ACTION_ITEMS.md)，每条有 owner 与截止；
- [ ] 级别与影响面定稿（升降级理由已记录）；
- [ ] 需要更新的 runbook / 告警 / 矩阵已提交 PR（或已建行动项跟踪）。

关闭后在 24 小时内发出复盘初稿（P1 5 个工作日内完成复盘会）。

---

## 7. MUST NOT

- 未定级就开始长时间排查（P1 超过 15 分钟仍无声明）；
- 无 IC 的多头指挥，或绕开 IC 在生产改配置；
- 用「已恢复」代替关闭标准，跳过数据校验与行动项登记；
- 在事故频道粘贴密钥、令牌、完整连接串或未脱敏的用户数据；
- 把复盘写成追责材料——复盘只对流程与系统，不对个人。
