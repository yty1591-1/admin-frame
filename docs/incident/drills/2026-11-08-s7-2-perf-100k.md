# S7-2 性能实测（10 万档位）：单活动规模上限抬升后的真实代价

| 字段 | 内容 |
|---|---|
| 场景 | S7-2 / §8 指标「证据导出 10 万行 ≤2 min」在当前实现下是否可达 |
| 形态 | **集成实测（真实 MySQL + Redis）**，单连接串行、无并发；不是 staging 集群 |
| 日期 | 2026-11-08 |
| 环境 | 本机 `docker-compose.integration.yml`：MySQL 8.0.46（`admin_frame_test`）、Redis 7、Go 1.26.10 |
| 被测路径 | `ActivateCampaign`（`generateTasks` + `SaveAll` + `CountByCampaign` + 活动回写）、`ExportEvidence` |
| 用例 | `tests/integration/iam/mysql_certification_perf_test.go`（`IAM_PERF_DRILL=1` 开启） |
| 证据 | [artifacts/2026-11-08-s7-2-perf-100k/summary.json](./artifacts/2026-11-08-s7-2-perf-100k/certification-perf-summary.json)、[证据样本 CSV](./artifacts/2026-11-08-s7-2-perf-100k/certification-perf-evidence-sample.csv) |
| 关联决策 | [ADR-0012 单活动规模上限与导出口径](../../adr/0012-certification-export-limit.md)（Proposed） |

> **生产默认值未改动**：`MaxTasksPerCampaign` 仍为 10000。本轮用测试侧覆盖
> （`CERT_DRILL_MAX_TASKS=100000`）量「若抬到 10 万要付什么代价」，不是既有行为变更。
> 1 万档位的基线与本轮改动前一致，见 [S7-2 实测（1 万）](./2026-11-08-s7-2-perf.md)。

## 1. 结论

| 指标 | 目标 | 10 万实测 | 判定 |
|---|---|---|---|
| 复核清单生成 10 万主体 | ≤ 5 min | **4.68 s**（两次 4.683 / 4.697 s） | 达标，余量约 64 倍 |
| 证据导出 10 万行 | ≤ 2 min | **479–595 ms / 14 300 132 B** | 达标，余量约 200 倍 |
| 默认上限仍为 10000 | 不因规模演练被抬高 | 第 10001 条仍被拒（`exceeds limit`） | 符合预期 |

结论：**10 万行导出在抬升上限后是可达的，且离指标有两个数量级余量**。此前「不可达」的成因是
单活动装不下 10 万个主体，不是导出慢。是否抬升属容量决策，见 ADR-0012。

## 2. 与 1 万档位对照

| 观测项 | 1 万 | 10 万 | 倍数 |
|---|---|---|---|
| 清单生成（全量范围） | 529 ms | 4 683–4 697 ms | 8.9× |
| 清单生成（`PrivilegedOnly=true`） | 454 ms | 4 828–5 090 ms | 10.6× |
| 落库语句数 `Com_insert` | 23 | 203 | 8.8× |
| 特权判定 `Com_select` | 6 | 6 | **1×** |
| 证据导出 | 43 ms / 1 430 132 B | 479–595 ms / 14 300 132 B | 11× |
| 造数（raw SQL，500 行/批） | 500 ms | 4 239–7 604 ms | 8.5–15× |

三条判读：

1. **落库仍按批**：203 条语句 = 200 批（10 万 / 500）+ 3 条元数据。语句数随规模线性增长，
   说明批量插入没有退化成逐条（逐条会是 100 003 条）。
2. **特权判定与规模解耦**：两种规模下都是 6 条查询（3 条角色 + 3 条元数据）。按角色去重的
   缓存不随主体数增长失效。
3. **导出线性**：行数 ×10，耗时 ×11–14、体积 ×10。没有隐藏的 N+1 或重复编码。

## 3. 测试侧如何抬上限

生产配置没有暴露该上限（`certificationLimits()` 未映射 `MaxTasksPerCampaign`），
所以本次只能用测试装配覆盖：

- `CERT_DRILL_MAX_TASKS=100000`：`newCertDrillEnv` 把它写进 `CertificationLimits.MaxTasksPerCampaign`；
  未设置时传 0，走服务内置默认 10000，**与生产缺省行为一致**。
- 场景 4 的「默认上限」边界改为使用独立的 `env.defaultLimit`（强制 0 → 默认 10000），
  与规模场景解耦：无论规模演练把上限抬到多少，「默认值仍是 10000」始终被单独验证。
- `IAM_PERF_BINDINGS > 上限` 时用例直接失败并提示需同时设 `CERT_DRILL_MAX_TASKS`，
  避免把「被上限拒绝」误读成「生成慢」。

## 4. 内存与事务代价

| 观测项 | 10 万 | 口径 |
|---|---|---|
| 生成期累计分配 `TotalAlloc` | **365.6 MB**（3.6 KB/任务） | 本次生成真实申请过的内存总量，含批缓冲与 SQL 参数 |
| 生成期堆驻留增量 `HeapInuse` | **+67.8 MB** | 生成期间存活对象抬升，反映持续占用 |
| `ActivateCampaign` 事务时长 | **4.68 s** | 200 批全部在同一事务内；失败整体回滚 |

按 3.6 KB/任务线性外推：100 万主体约需 680 MB 驻留、单事务数十秒——这是
「不建议把默认值抬到 10 万以上」的依据，也是 ADR-0012 里对该档位设前置条件的原因。

内存采样（`runtime.ReadMemStats`）放在计时区间之外：它带 STW，混进耗时会让毫秒级数字失真。
`TotalAlloc` 而非 `HeapAlloc`：生成结束后任务对象可能被回收，`HeapAlloc` 会低估。

## 5. 本次未声称完成的部分

- **并发争用**：单连接串行，2–3 个活动同时生成时的事务等待、慢查询、连接池占用均未量。
- **staging 同量级复测**：本地单机，未在 staging 用真实主体规模验证（复用 AI-05 窗口）。
- **网关响应体**：14.3 MB 单次响应经入口网关时的缓冲与超时配置未核对。
- **清理与扫描争锁**：单活动 10 万行时保留期清理、超期扫描的锁竞争未量。
- **上限调整本身未实施**：本轮只出实测与决策依据，配置项与默认值均未改。

## 7. 复跑方式

```bash
docker compose -f docker-compose.integration.yml up -d --wait mysql redis
export IAM_TEST_MYSQL_DSN="app:app@tcp(127.0.0.1:3306)/admin_frame_test?parseTime=true&loc=UTC"
export TEST_REDIS_ADDR="127.0.0.1:6379"
export IAM_PERF_DRILL=1
export IAM_PERF_BINDINGS=100000
export CERT_DRILL_MAX_TASKS=100000            # 必须 ≥ IAM_PERF_BINDINGS，否则用例提前失败
export CERT_PERF_ARTIFACT_DIR="$(pwd)/docs/incident/drills/artifacts/2026-11-08-s7-2-perf-100k"
go test ./tests/integration/iam/ -run TestCertificationPerf10kOnMySQL -v -count=1 -timeout 15m
```

单次全程约 19–39 s（含造数）；造数耗时抖动主要来自容器冷启动与 fsync。
