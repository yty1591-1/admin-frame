# S7-2 性能实测：10k 主体清单生成与证据导出

> 执行日期：2026-11-08 · 环境：MySQL 8.0.46 + Redis 7（`docker-compose.integration.yml`）
> 用例：`tests/integration/iam/mysql_certification_perf_test.go`（默认跳过，`IAM_PERF_DRILL=1` 开启）
> 证据：`artifacts/2026-11-08-s7-2-perf/`（summary.json / 证据样本 CSV / 完整测试输出）

## 1. 结论

| 计划 §8 指标 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 复核清单生成 10k 主体 | ≤ 5 min | **403–767 ms**（7 次运行区间） | 达标，余量约 390 倍 |
| 证据导出 10 万行 | ≤ 2 min | **不可达**：单活动上限 10000 条，第 10001 条被拒 | 指标与实现上限冲突，需口径决策 |
| 证据导出 1 万行（实际上限） | — | 48–81 ms / 1 430 132 B | 线性外推 10 万行约 0.5 s、14 MB（**外推，非实测**） |

达标的前提是本次修掉的两处写放大；未修前 10k 全量需 13.79 s、特权场景需 49.55 s，虽仍低于 5 min，
但按同斜率外推 10 万主体会到 8 分钟以上，直接破线。

## 2. 环境与口径

- 数据：10 000 条生效绑定（1 个角色），`channel=admin`，`expires_at` 为空，`revoked_at` 为空。
- 造数用 raw SQL 批量插入（500 行/条语句），耗时单独记为 `seed_ms`，不计入被测路径。
- 被测路径：`ActivateCampaign`（内部 `generateTasks` + `SaveAll` + `CountByCampaign` + 活动回写）。
- 语句计数：`SHOW GLOBAL STATUS` 的 `Com_insert` / `Com_select` 前后差值。测试进程独占 integration 库，
  `reset()` 里的 `DELETE` 不增 `Com_insert`，差值即本用例产生的语句数。
- 重复运行 6 次，抖动主要来自容器冷启动与 fsync；下文取代表性一组。

## 3. 优化前基线

| 场景 | 耗时 | 语句增量 | 说明 |
|---|---|---|---|
| 清单生成 10k（全量范围） | 13.79 s | `Com_insert +10003` | 每条任务一次 INSERT 往返 |
| 清单生成 10k（`PrivilegedOnly=true`） | 49.55 s | `Com_select +30003` | 每条绑定 3 次查询（角色 + 权限 + 数据范围） |
| 证据导出 10k 行 | 59 ms | — | 单次全量查询 + 编码，无 N+1 |

两处写放大的根因：

1. `SQLCertificationTaskRepository.SaveAll` 是 `for ... ExecContext` 逐条插入，10k 任务 = 10k 次往返，
   全部在 `ActivateCampaign` 的单个事务内。
2. `generateTasks` 在 `PrivilegedOnly=true` 时对每条绑定调 `isPrivilegedRole`，而 `SQLRoleRepository.FindByID`
   一次要 3 条 SQL（角色、权限、数据范围），10k 绑定 = 3 万次查询。

## 4. 修复

### 4.1 任务按批多值插入

`internal/iam/infrastructure/persistence/mysql_certification.go`：`SaveAll` 改为每批
`certificationTaskInsertBatch = 500` 行的多值 `INSERT`，保留 `ON DUPLICATE KEY UPDATE id = id` 的幂等语义。
16 列 × 500 行 = 8000 个占位符，低于 MySQL 65535 上限，单批约 100 KB。

契约不变：分批仍在调用方事务内，任一批失败即返回错误、由事务回滚全部批次（「全成或全不成」）。

### 4.2 特权判定按角色去重

`internal/iam/app/certification_service.go`：`generateTasks` 内加 `privilegedCache map[string]bool`，
同一角色只判定一次。缓存生命周期仅限本次活动生成，角色在生成期间不可变，语义与逐条判定等价。

不做跨活动缓存：角色权限可在两次复核之间变更，跨活动缓存会让清单漏掉新晋高危角色。

## 5. 优化后实测

| 场景 | 耗时 | 语句增量 | 相对基线 |
|---|---|---|---|
| 清单生成 10k（全量范围） | 445 ms | `Com_insert +23`（20 批 + 3 条元数据） | 约 20 倍 |
| 清单生成 10k（`PrivilegedOnly=true`） | 418 ms | `Com_select +6`（3 条角色查询 + 3 条元数据） | 约 100 倍 |
| 证据导出 10k 行 | 48–81 ms | — | 持平 |
| 审计投递 | 109 条事件，`pending=0 / dlq=0` | — | — |

## 6. 上限边界：10 万行导出当前不可达

`MaxTasksPerCampaign` 默认 10000（`certification_service.go:126`）。实测第 10001 条绑定时
`ActivateCampaign` 返回 `certification task count exceeds limit`，活动不落地、任务不生成。

因此「证据导出 10 万行 ≤ 2 min」在当前实现下**无法用单个活动达成**。三条可选路径：

1. **提高单活动上限**到 ≥ 100000。按 500 行/批估算约 200 批；参照本次 10k = 23 批 445 ms，
   10 万行预计 4–6 s（**估算，需实测确认**）。代价是单事务持锁时间变长、活动回写前的内存驻留变大。
2. **改指标口径**为「多活动累计 10 万行」，即 10 个 1 万行的活动分别导出。实现零改动，
   但导出接口仍受单活动限制，运维需按活动分批取。
3. **导出改流式**（分页读 + 边读边写响应）。这解决的是内存与响应体大小，不解决上限；
   若同时要提高上限，需要一起做。

本次不擅自改动上限默认值：容量上限属产品与容量决策，须随 staging 压测（AI-05 窗口）与 SRE 评估后调整。
报告给出的是三条路径与实测依据，不是既成决定。

## 7. 证据字段完整率（S7-4 待量化项）

「导出字段完整率 100%」必须按**状态应填口径**统计，不能按全列非空统计：

| 数据集 | 行数 | `decision` | `reason` | `decided_by` | `decided_at` |
|---|---|---|---|---|---|
| 未裁决（全部 `pending`） | 10 000 | 0 | 0 | 0 | 0 |
| 已裁决（全部 `confirmed`） | 100 | 100 | 100 | 100 | 100 |

- `pending` 任务的裁决四列为空是正确语义——未裁决本就没有裁决依据。按全列算会得到 0%，
  那是口径错误，不是缺陷。
- 已裁决任务四列 100% 齐备：等保与 SIEM 消费方可以按 `task_id` 追到裁决人、时间与理由。
- 补充口径（S7-5 演练已确认）：自动过期（`auto_expire`）的任务 `decided_by`/`reason` 列为空，
  操作人只存在于 `rbac.certification` 审计事件；证据消费方必须以审计事件为准。

结论：**「导出字段完整率 100%」在应填口径下成立**（已裁决任务四列全 100%），
未裁决行按语义留空并在消费侧区分状态。

## 9. 复现方式

```bash
docker compose -f docker-compose.integration.yml up -d --wait mysql redis

IAM_PERF_DRILL=1 \
IAM_PERF_BINDINGS=10000 \
IAM_TEST_MYSQL_DSN='app:app@tcp(127.0.0.1:3306)/admin_frame_test?parseTime=true&loc=UTC' \
CERT_PERF_ARTIFACT_DIR="$(pwd)/docs/incident/drills/artifacts/2026-11-08-s7-2-perf" \
go test ./tests/integration/iam/ -run TestCertificationPerf10kOnMySQL -v -count=1
```

用例内含 5 组断言，任一退化即失败：

1. 任务数 = 绑定数（清单覆盖全部生效绑定）；
2. `Com_insert` 增量 ≤ 任务数的 1/10（落库必须是批量，退回逐条即红）；
3. `Com_select` 增量 ≤ 10（特权判定必须按角色去重，退回 N+1 即红）；
4. 导出行数 = 任务数，且必需列齐全；
5. 已裁决任务证据四列 100% 非空；超上限活动被拒且错误含 `exceeds limit`。

单测层另有两条与规模无关的锚点（`certification_perf_contract_test.go`）：
1 角色 3 绑定只查 1 次角色；`SaveAll` 只被调用 1 次且行数等于任务数。
性能用例默认跳过，这两条锚点保证 CI 里也能拦住退回逐条实现。
