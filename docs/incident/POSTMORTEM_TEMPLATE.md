# 复盘模板（Postmortem，blameless）

> 复制本文件到 `docs/incident/reviews/INC-YYYYMMDD-NN.md` 后填写；未通过复盘的行动项不得标 `done`。  
> **原则**：对系统与流程，不对个人。任何「某人没注意」都要继续追问「为什么系统允许这个疏忽造成影响」。

| 字段 | 内容 |
|---|---|
| 事件 ID | INC-YYYYMMDD-NN |
| 级别 | P1 / P2 / P3（定稿级别，含升降级理由） |
| 起止（UTC） | 2026-11-05T00:12Z → 2026-11-05T01:10Z |
| 影响时长 | 用户可见影响共 N 分钟 |
| 检测用时 | ONSET → DETECT：N 分钟 |
| 确认用时 | ONSET → ACK：N 分钟 |
| 缓解用时 | ONSET → MITIGATE：N 分钟 |
| 检测方式 | 告警 ID / 用户反馈 / 巡检（若靠用户反馈，必须列为缺口） |
| IC / 参与人 | … |
| 状态 | draft / reviewed / closed |
| 关联发布 | image digest `sha256:…` 或「无发布」 |
| 关联行动项 | AI-YYYY-MM-DD-NN（与台账一致） |

## 1. 摘要

三句话：发生了什么、影响了谁、怎么止住的。不写过程细节，细节放时间线。

## 2. 影响

| 维度 | 量化 |
|---|---|
| 受影响端 | A / B / C / worker |
| 受影响租户数 | N（占总量 M%） |
| 失败请求数 / 比例 | N 次 / M% |
| 数据影响 | 无 / 错误 N 条 / 删除 N 条 / 泄露字段（列明） |
| 资金或合同影响 | 无 / 需补偿（金额与依据） |
| SLO 影响 | 错误预算消耗 M%（对本季度冻结策略的影响） |

「无数据影响」必须给出验证方式（校验查询、对账结果），不能只写结论。

## 3. 时间线

UTC，一行一条，标记与 [RESPONSE.md](./RESPONSE.md) §3 一致：

```text
2026-11-05T00:12:31Z [ONSET]    …
2026-11-05T00:14:02Z [DETECT]   …
2026-11-05T00:16:40Z [ACK]      …
2026-11-05T00:18:10Z [DECLARE]  …
2026-11-05T00:31:00Z [MITIGATE] …
2026-11-05T01:05:00Z [RECOVER]  …
2026-11-05T01:10:00Z [CLOSE]    …
```

## 4. 根因

### 4.1 直接原因

触发故障的那一次变更 / 依赖故障 / 流量形态，附证据（提交、digest、依赖状态、查询）。

### 4.2 5 Whys

1. 为什么用户看到 5xx？→ …
2. 为什么会出现该错误？→ …
3. 为什么测试/审查没拦住？→ …
4. 为什么监控没更早发现？→ …
5. 为什么流程允许这个变更直接到生产？→ …

第 3、4、5 问必须落到**可改的机制**（测试类型、门禁规则、发布阶段、告警表达式），否则继续追问。

### 4.3 做对了什么

保留有效动作（例如：自动回滚生效、告警 2 分钟内触达），避免下次「一刀切加流程」把有效机制也砍掉。

## 5. 行动项

| ID | 类型 | 行动项 | 负责人 | 截止 | 验证方式 | 状态 |
|---|---|---|---|---|---|---|
| AI-YYYY-MM-DD-01 | prevent | … | @role | YYYY-MM-DD | 具体测试名 / 指标 / 脚本输出 | open |

规则：

- 类型只能是 `prevent`（消除根因）、`detect`（更早发现）、`mitigate`（缩短影响）；
- **验证方式必须可执行**：测试用例名、`make` 目标、指标表达式、演练场景 ID；
- 禁止不可验证项（「加强培训」「提高意识」「注意规范」）——要写就把行为写具体（如「发布前必须跑 X 脚本」）；
- 台账同步：[ACTION_ITEMS.md](./ACTION_ITEMS.md)；逾期未关闭须在周会说明，不得静默延期。

## 6. 附录

- 仪表盘 / 查询链接（含时间范围）
- 关键日志摘录（已脱敏）
- 相关 PR / 发布记录 / digest
- 演练或压测证据（若与本事件相关）
